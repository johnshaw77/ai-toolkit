# 談出一份 SPEC.md

使用者想做的東西：`$ARGUMENTS`

## ⚠️ 這個指令要問問題

平常的規則是「不要停下來問」。**這裡相反。**

使用者此刻就在電腦前，而且這是他交出任務前**最後一次能澄清的機會**——
之後無人值守跑起來就沒人能回答了。規格含糊的代價會在幾小時後才顯現。

所以：不清楚就問，但**問得有效率**（用 AskUserQuestion 一次問完，不要一題一題來）。

## 先確認這是第幾輪

看專案根目錄有沒有 `SPEC.md`。

### 沒有 → 第一輪，直接往下走

### 有 → 這是後續的一輪，先處理舊的

**SPEC.md 是「這一輪的工單」，不是會長大的產品說明書。** 累積會讓後續每一輪
都得重讀已完成的項目、重驗整個產品，而且很快就沒人讀得下去。

所以：

1. 讀舊的 `SPEC.md`，再看 `README.md` 和 `git log --oneline`，判斷**哪些項目
   真的完成了、哪些沒有**。勾選狀態是起點（`- [x]` 完成、`- [-]` 被跳過、
   `- [ ]` 沒做到），但不要全信——不確定就跑一次測試看看。
2. 把舊的整份搬到 `docs/specs/<YYYY-MM-DD>-<簡述>.md`（目錄沒有就建）。
   開頭加一行「本輪結果：完成 F1–F5，F6 未完成，原因……」。
3. 新的 `SPEC.md` 只包含兩種東西：
   - 上一輪**沒做完**的項目（原樣帶過來，重新編號，勾選一律重設成 `- [ ]`）
   - 這一輪的**新**項目
4. 已完成的項目**不要**再出現在 SPEC.md 裡——它們的紀錄在 README（功能總覽）、
   `docs/DECISIONS.md`（取捨）、`docs/VERIFICATION.md`（驗證）和歸檔的舊 spec 裡。

寫新規格時要**讀過既有程式碼**：新功能常常要接既有的模組，規格要寫清楚
「F7 用 F2 已經做好的 scheduler，不要另外寫一套」這種銜接關係。

## 步驟

### 1. 先看專案現況

用 Bash 看一眼：有沒有 `package.json` / `pyproject.toml` / `go.mod`、
有沒有 `docker-compose.yml`、是不是 monorepo、`scripts` 裡有哪些指令。

**完成條件要照專案實際情況寫**——是 `npm test` 還是 `pytest`、
dev server 在哪個埠、要不要 `docker compose up`。寫錯了守門員會擋不到。

### 2. 把功能拆成可驗收的項目

每項要能獨立判斷「做完了沒」。編號 F1、F2……，每項寫：

- 做什麼（一兩句）
- **這一項自己的完成條件**（客觀、可檢查）

**格式是固定的**，每項的標題行必須是頂格的核取方塊：

```markdown
- [ ] **F1** 卡片 CRUD：新增、編輯、刪除卡片，資料存在 SQLite
  - `pytest tests/test_cards.py` 全綠，至少 8 個案例
  - `POST /api/cards` 缺 `front` 回 400
```

- 標題行頂格寫 `- [ ] `；完成條件**縮排**、用一般的 `-`，**不要**再用核取方塊。
- 執行者完成一項就改成 `- [x]`，跳過就改成 `- [-]`。

這不是排版偏好：SPEC.md 的勾選狀態就是**進度存在檔案裡的地方**。脈絡被壓縮後、
或 `unattended --loop` 每項開一場新對話時，執行者只能從這裡知道做到哪；
迴圈也是靠數「頂格的 `- [ ] `」來判斷還剩幾項、有沒有進展。

拆得太粗（「做一個後台」）無法驗收；太細（「新增一個按鈕」）沒必要。
合適的粒度是**一項對應一顆 commit**。

### 一輪放幾項：5–10 項，超過就切輪

項目太多時風險是**尾端集中**的：前幾項在乾淨脈絡下做，品質好；第四十項是在
壓縮過好幾次的脈絡下做的，而使用者回來時最可能只抽查前面幾項——**品質最差的
地方剛好是他最不會看的地方**。

無人值守期間沒有人能 `/clear`，所以脈絡只會愈來愈髒。控制髒的程度的唯一辦法
是**縮短單輪的長度**。

所以清單超過十項左右時，不要硬塞成一輪：挑出這一輪真正要的，其餘明講「留到
下一輪」。使用者想一次做完五十項的話，告訴他切成五、六輪、每輪之間花五分鐘
審一次，總時間差不多但每輪都是在乾淨脈絡下跑的。

### 3. 寫「完成的定義」——這節最重要

必須客觀到**無法自我欺騙**。對照：

| ❌ 含糊 | ✅ 客觀 |
|---|---|
| 測試要充足 | `npm test` 全綠，且 F1+F2 的測試合計不少於 15 個案例 |
| UI 要能正常使用 | Chrome MCP 走過：新增 → 練習 → 翻面 → 答對答錯 → 看到總結 |
| 程式碼品質要好 | `npm run typecheck` 無錯誤、console 零 error/warning |
| API 要能用 | `POST /api/x` 正常路徑回 201、缺欄位回 400 且訊息指出欄位名 |

**看到含糊的條件就要當場改掉**，不要照抄使用者的原話。可以直接問：
「『測試要充足』我想改成『不少於 N 個案例』，N 你覺得多少合理？」

固定要包含的幾條（依專案調整）：

1. 測試全綠（用這個專案實際的指令）
2. 型別檢查通過（如果有）
3. UI 改動用 Chrome MCP 實際走過流程；後端改動實際打過 endpoint
4. console 零 error、零 warning
5. 文件寫到正確的地方：`README.md`（改寫，精簡）、
   `docs/DECISIONS.md`（追加取捨）、`docs/VERIFICATION.md`（追加驗證結果）

### 4. 寫「實作順序」

`F1 → F2 → …`，並註明**每完成一項就跑一次測試**，不要全部寫完才驗。
清單的**排列順序就是實作順序**——`--loop` 永遠挑第一個 `- [ ]` 來做。
順序上讓「純邏輯、可單元測試」的項目排前面，UI 排後面。

### 5. 寫「取捨授權」——沒有這節，無人值守會卡住

明確列出哪些細節可以自己決定。例如：

> 規格沒寫到的細節（配色、排版、元件怎麼拆、要不要動畫、錯誤訊息用字）
> 一律自行決定，選你認為最好的做法，把理由寫進 `docs/DECISIONS.md`。
> 不要為了這類問題停下來詢問。

也要寫**卡住時怎麼辦**：

> 同一項嘗試兩次仍無法解決就跳過（該項改成 `- [-]`），繼續下一項，
> 最後在 README 的「未完成事項」說明卡在哪、試過什麼。

### 6. 寫檔並提醒

把內容寫進專案根目錄的 `SPEC.md`。**永遠是覆蓋，不是追加**——舊的已經在
上面那步歸檔到 `docs/specs/` 了。

### 6.5 順手把對話存檔打開

`<專案>/docs/transcripts/` **不存在的話**，執行一次：

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/transcript2html.py" --here
```

已經存在就跳過，不用重跑。

為什麼在這裡做：那個資料夾的存在**就是自動存檔的開關**，而寫完規格就等於
要動工了——這是使用者最後一次還在現場的時機。等他走人之後才發現沒開，
整輪過程就只剩 `~/.claude/transcripts/` 的全域封存，沒有放在專案裡、
可以直接開來看或分享的那一份。

回報時附一句「對話存檔已啟用，回來後開 `docs/transcripts/index.html` 調閱」。

（`/unattended:mode` 也會做同一件事。兩邊都做是刻意的——使用者可能只跑其中一個。）

寫完後回報時**一定要包含這四點**：

1. 請他**現在就讀一遍**——這是最後的把關機會，交出去之後沒人能澄清。
2. 特別點出**你自己覺得最可能被誤解的那一兩項**，請他確認。
3. **讀完、確認過之後先 `/clear`，再開始跑。** 這一點要講，不要省略——
   理由見下面那節。
4. 下一步怎麼跑：
   ```
   /clear
   git checkout -b feat/<名稱>
   /unattended:mode 依 SPEC.md 完成全部功能
   ```
   要真的走人的話，先把 Claude Code 跑在 tmux 裡（見 README）。

   項目多、預期會跑很久的話，另外提一句可以改用
   `unattended --loop`：每一項開一場全新的對話，脈絡不會愈跑愈髒
   （沒裝過 `unattended` 指令的話先跑 `/unattended:install-bin`）。這條路不用 `/clear`——每一輪本來就是乾淨的。

### 為什麼要先 /clear

使用者聽到這個建議，第一個反應通常是**「我剛審完就清掉，那不是白審了？」**
講的時候要先把這點擋掉：

> 不會。審查的產出是**對 SPEC.md 的修改**，不是脈絡。
> 你抓到的每一件事只要寫回檔案就完整保留；沒寫回去的本來就會丟——
> 所以**要改就趁現在改完再清**。

| 這個動作 | 誰在做 | 產出到哪 |
|---|---|---|
| 審一遍 | 使用者（人）讀 SPEC.md | 發現寫錯 → **改 SPEC.md** |
| `/clear` | 清掉對話 | 檔案完全不受影響 |
| 開工 | 新的 session 讀 SPEC.md | 看到的是改過的定稿 |

擋掉之後，再講為什麼非清不可：

- **無人值守的執行者本來就問不到人。** 使用者走了之後，它手上就只有 SPEC.md。
  與其讓它在「還記得談話內容」的狀態下跑、把靠記憶補完的漏洞藏起來，
  不如現在就清乾淨，**逼規格自己證明它站得住**。
  清完發現它不知道某件事 → 代表 SPEC.md 漏寫了，而此刻使用者還在，補五分鐘就好。
  這是一次成本為零、而且失敗還救得回來的壓力測試。
- **談出來的草案有一半是被推翻的。** 剛才提過又否決掉的做法還留在脈絡裡，
  執行時可能被當成有效資訊撿回去用。SPEC.md 是定稿，那才是唯一該看的東西。
- **無人值守要跑好幾個小時，脈絡越乾淨能做的越多。** 談規格常常吃掉可觀的
  額度——讀專案、來回問答、寫了又改的草稿。帶著這些去跑，會更早遇到自動壓縮，
  而壓縮丟掉的往往正是 SPEC 的細節。
- **不需要靠記憶。** `/clear` 之後它會重新讀 `SPEC.md`；工作準則也還在，
  因為 `/clear` 會以 source `clear` 重跑一次 SessionStart hook。

所以順序是：**讀過 SPEC → 要改就改完 → `/clear` → 開分支 → `/unattended:mode`**。

### 反過來說，這也是對 SPEC.md 的要求

規格必須**在沒有任何對話脈絡的前提下可執行**。`/spec` 產出的四個區塊，
每一塊都是為了這件事而存在的：

| 區塊 | 讓執行者不必問什麼 |
|---|---|
| F1、F2… 各自的完成條件 | 「這項算做完了沒」 |
| 完成的定義 | 「測試要寫多少才夠」 |
| 實作順序 | 「先做哪個」 |
| 取捨授權 | 「配色用什麼」 |

寫規格的時候就用這個標準自我檢查：**如果這份 SPEC 少了脈絡就跑不動，
那它還沒寫完。**

### 什麼時候不該建議 clear

使用者其實還要**繼續跟它一起做**、只是想讓它多跑一段的時候。那不是無人值守，
是互動開發的延長，脈絡當然要留著。

`/clear` 只建議在「規格定稿、真的要走人」這條路徑上，不要見人就講。

## 不要做的事

- 不要開始寫實作程式碼。這個指令只產出規格。
- 不要把技術選型的理由寫進 SPEC——那是事後 `docs/DECISIONS.md` 的內容。
- 不要照抄使用者的含糊描述當完成條件。
